## Governing Overview

[application route overview](overview.md)

## Purpose

The external projection operation: it renders each requested knowledge view into its declared sibling formats and hands the whole plan to the projection writer, which is the only write path an artifact takes to a destination. Its own docstring states the shape it enforces — Markdown and JSON "are sibling views from the same resolved records", they "are rendered by the same renderer/profile version", and "neither is the portable export -- that is ``KS-R06@v1``'s different contract" — and the same docstring states the property that makes it safe to call: "**The renderer places authored text; it does not produce it.**" **It deliberately has no model call, no summary, no score and no reassessment**, so "Requirement 4.4's \"renderers do not call an LLM to invent fresh explanation\" is therefore true of this module by construction -- the only functions it contains build strings out of the payload it was handed". It also holds no store, opens no dataset of its own beyond the shipped read context, decides no classification, writes no file directly, and mints no identity: a payload whose snapshot cannot be read is not projected at all but reported as an unresolved projection input, and the destination path it derives is deliberately not a knowledge identity.

## Code Commentary

### Logic

**Markdown and JSON are two sibling renderings of one resolved record set, and one version covers both.** `render_payload_as_markdown(payload, subject)` and `render_payload_as_json(payload, subject)` consume the same `ViewPayload` and carry the same recorded values: the first writes the renderer/profile version, the source snapshot's `logical_digest`, the schema generation, the completeness statement and the declared scope as a header block, and the second writes them as `rendererVersion`, `sourceSnapshot` and `schemaVersion` keys of one JSON object. The two never disagree about the version they were produced by, because `PROJECTION_PROFILE_VERSION = VIEW_RENDERER_VERSION` is the module's own alias of the views seam's recorded value rather than a second literal a second renderer could drift from, and both renderers read `payload.renderer_version` off the payload they were handed.

**Neither rendering is the portable export, and the marker is written into the artifact itself.** `PROJECTION_NOT_AN_EXPORT` names the file "a projection of resolved knowledge records, not a portable database export" and states that "The complete portable round trip is a different contract"; the Markdown renderer appends it as a blockquote and the JSON renderer writes it as the leading `projectionNote` key. The reason it is spelled in the artifact rather than only in this card is stated at the constant: the marker exists "so a reader who finds the file cannot mistake it for ``KS-R06@v1``'s portable round trip" — the export contract belongs to another leaf, and a projection that could be read as it would be a claim this operation has no authority to make.

**The renderer places authored text and composes none, which is why requirement 4.4 holds by construction.** `_row_markdown(row)` reads the row's own fields — its ordered position, its ordering input, its provenance, its subject, its essential conditions, its statement, its consequence and its assessment status — and emits them with their provenance; `_consequence_markdown(consequence)` renders one no-consequence statement together with the class that produced it and, when the class is authored, the author ref and the stored claim ref it cites. Nothing in either function calls a model, summarizes a statement, scores a row or reassesses a disposition, so "a displayed disposition is the recorded disposition; a displayed status is the stored status; an unassessed claim renders as unassessed rather than as favourably assessed". The docstring's claim is therefore structural: the only functions this module contains build strings out of the payload they were handed.

**Every artifact either carries the three recorded values or is never emitted.** `_output(payload, subject, relative_path, declared_format, text)` constructs the `RenderedOutput` with `stable_identity=subject`, `source_snapshot=payload.snapshot.logical_digest` and `renderer_version=payload.renderer_version`, and `_outputs_for(payload, subject, profile)` builds one such output per format the destination profile declares, naming the file `{base}.md` or `{base}.json` from `_document_path`. `project_knowledge(database_path, profile, requests, options)` is the operation that owns the refusal: when `read_knowledge_view` returns a refused result or no payload, it returns `refusal_report(...)` carrying a `ProjectionRefusal` coded `unresolved_projection_input`, whose detail says no artifact is emitted without "the identity, snapshot and renderer version requirement 4.3 requires". Only after every requested view resolves does it build the `ProjectionPlan` — destination, outputs and `authorized_overwrites` — and hand it to `ManagedProjectionWriter`.

**The destination is derived from the view and the recorded identity, never from a symbol name or a path.** `_document_path(payload, subject)` sanitizes the projected subject into one path segment and returns `f"{payload.view}/{safe or 'unidentified'}"`, so the artifact's location is a function of the view name and the stable identity the artifact records. Its docstring refuses the alternatives by name — "never from a symbol name, a path prefix, a directory depth or a file extension" — and states what happens when two records would land on one path: "Two records with equal identities would collide here, and the writer reports that as a collision rather than disambiguating it." The module therefore adds no disambiguation, no suffix and no tiebreak of its own.

**Conditions travel with the invariant, and an omission is written rather than performed.** `_row_markdown` places the row's essential conditions **before** the statement whose application they qualify, which is the position requirement 4.8 asks for, and it has two exits rather than one: when `essential_conditions` is non-empty each condition is written as a sub-item, and when it is empty but `conditions_omitted` is set the renderer writes `- essential conditions: **omitted by this view's scope**`. A compact projection may therefore shorten prose it is licensed to shorten and may not silently drop the conditions under which the invariant applies — the omission is a fact the artifact states about itself.

**A detection signal and an authored description stay separately attributed, and the payload has no field that merges them.** Each row is rendered with its provenance class beside its value: `authored` rows name their `author_ref` and rationale, `mechanical` rows name their `rule_id` and `rule_version`, and a row whose assessment status is `missing` adds `- assessment: **none recorded**` rather than an empty class. `_consequence_markdown` makes the same split for the no-consequence statement. Because each block carries its own provenance line, requirement 4.9 holds at the rendering layer too: there is no merged field combining a detection signal with an authored description for a reader to attribute incorrectly.

**One operation value, one writer, and a refusal path that shares the writer's report type.** `ProjectionOptions` is the frozen value carrying `repository_root`, `code_tree_id`, `authorized_overwrites` and `hooks`, so one projection is configured as one value rather than seven arguments; `authorized_overwrites` is "the explicit per-path caller authorization requirement 5.8 makes the only route to replacing an externally edited file", and `hooks` is the interruption seam the vault-safety case drives. `project_knowledge` opens the read context once through the shipped `open_read_context`, refuses an empty request tuple as a caller error before opening anything, and returns `ProjectionReport` from `ManagedProjectionWriter.write` on both the refused and the projected path, so a caller reads one report shape either way.

### Conventions

Public surface is declared rather than implied: `__all__` names exactly five entries — `PROJECTION_PROFILE_VERSION`, `ProjectionOptions`, `project_knowledge`, `render_payload_as_json` and `render_payload_as_markdown` — and the private helpers (`_outputs_for`, `_output`, `_row_markdown`, `_consequence_markdown`, `_document_path`) stay module-local, so the renderers a caller may drive are named ones and the composition around them is not re-exported by accident. Shapes and vocabularies that other modules already own are imported rather than re-declared: `RenderedOutput`, `ProjectionPlan`, `ProjectionRefusal`, `ProjectionReport` and `DestinationProfile` come from `models/knowledge/projection_manifest.py`, `ViewPayload` and `ViewRequest` from `models/knowledge/view.py`, and the writer, its `ProjectionHooks` seam and `refusal_report` from `memory/knowledge/managed_projection.py`. The renderer/profile version is likewise inherited: `PROJECTION_PROFILE_VERSION` aliases `VIEW_RENDERER_VERSION` instead of spelling a second string, so the projection profile and the views seam cannot disagree about which renderer produced a payload. Version and provenance values travel on the data — every output carries `payload.renderer_version`, every row carries its `provenance_class` — rather than being stated in prose a reader has to remember.

### Invariants And Boundaries

- **Both sibling views name one renderer/profile version, and it is the seam's value.** `PROJECTION_PROFILE_VERSION = VIEW_RENDERER_VERSION` and every `RenderedOutput` carries `payload.renderer_version`, so two artifacts produced by different renderer versions are distinguishable from the artifacts themselves.
- **A payload that cannot be read is not projected.** `project_knowledge` returns a `ProjectionRefusal` coded `unresolved_projection_input` for a refused or payload-less view, and emits no artifact for it; nothing downstream can observe a partially rendered plan from that call, because the write is never reached.
- **No artifact is emitted without the three recorded values.** `_output` always sets `stable_identity`, `source_snapshot` and `renderer_version`, and `RenderedOutput` declares all three as required bounded fields, so the type refuses the "rendered but missing its identity" case the docstring names.
- **The module computes no semantics.** There is no model call, no summary, no score and no reassessment anywhere in it; the Markdown and JSON bodies are built only from fields already present on the payload.
- **Every row is attributed beside its value.** An authored row names its author ref and rationale, a mechanical row names its registered rule and version, and an unassessed row says `none recorded` instead of rendering an empty class.
- **Conditions are never dropped silently.** They are written before the statement they qualify, and a view that could not carry them writes an explicit omission line instead.
- **The destination path is not an identity.** `_document_path` derives it from the view and the recorded subject and leaves collision handling to the writer; no digest, symbol name or extension participates in it.
- **The module writes no file and reads no dataset by itself.** Its only write route is `ManagedProjectionWriter.write(plan)`; the read route is the shipped `open_read_context` plus `read_knowledge_view`; both are imported ports rather than implementations here.
- **An empty request set is refused before any context is opened.** `project_knowledge` raises `ValueError` for an empty `requests` tuple, so a projection cannot proceed without at least one view request to resolve its namespace.
