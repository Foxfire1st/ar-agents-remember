# mcp/tests/test_reference_anchor_publication_owners.py

## Governing Overview

[mcp tests overview](overview.md)

## Purpose

`test_reference_anchor_publication_owners.py` protects MIK-R198 rules 5 and 7 through the public entry points of the sync and landing owners: `sync_result` in fast-forward and ordinary-merge mode and `record_landing_result` on a leaf. A merge reports the anchor debt it creates; every publication refuses it.

## Code Commentary

The pair is built rather than injected. Two real code sides move the cited source in the same file — the leaf rewrites the module docstring, the official line appends a function below the anchored ranges — and every memory side that commits re-records its anchors through the shipped `fix_references`, whose own answer is that nothing is left stale. What goes stale is the combination: the merged `app.py` blob is neither side's blob. `_clean` first settles two fixture properties that would otherwise be the refusal (a carried `realizes` anchor to a deleted source and a missing closed history), and `_author_the_merged_code_rows` answers the worklist from the product's own facts so no row can be mistaken for the reason. The recorded-landing case gives four answers on one entry and one world: `would-record` before the move, `refused` with `knowledge-gate-refused` and the anchor rule as the only rule after it, still refused after the worklist is answered, and `recorded` after the anchors alone are repaired.

## Evidence

- A memory fast-forward names the anchor debt of the pair it adopts [1]
- An ordinary merge names the debt two individually current sides create [2]
- A recorded leaf landing refuses the stale pair, does not waive it for answered rows, and records the repaired one [3]
- The merge that named the debt then refuses the publication and publishes the repaired pair [4]
