## Purpose

The rules the Architect and Orchestrator use when authoring or amending requirements and task structure, placing user controls or changing what the dashboard depends on. It grants no additional authority.

## Code Commentary

Requirement rules come first: test a requirement against every caller and phase named by touched records before freezing it; check inherited rules against the developer's directions before making them gates; link an existing table instead of copying it; name the existing structure (files, functions, who computes what) in the **Problem** section before fixing a new one, treating the developer's sentence as the aim; search recorded directions before amending; start a visible defect from the developer's picture or exact words and mark an unmeasured mechanism as a hypothesis; check what the harness itself does before adding a setting, default or handover rule; and treat a named provider or harness as a role setting, not a limit, unless the developer says otherwise.

Task structure: a task owns one primary packet and may own further approved packets of the same topic; one developer request is one task, and a split is proposed to the developer rather than made. A new task gets one major step per role (build, review, curation, knowledge check and landing), and an existing task gains a step only when the developer slots new scope into it. Before release to a Worker, the file sends the reader to the shared parallel-work and requirements-and-limits sections and the Architect role's delegation section, which govern disclosure and developer acceptance of added refusals, limits or narrowing. Control and dashboard rules close the file: a clickable control gets one named location, and before deferring, gating, moving or removing anything the dashboard depends on, the reader checks that the developer can use it with no agent active or brings the conflict to him.

The Architect role points here before authoring or amending a requirement and its task structure; the planning operation links the topic-merge section before grouping same-topic packets.

## Evidence

- Requirement changes are tested against callers and phases, prior directions and the existing structure before being fixed. [1]
- Harness behaviour is checked before adding rules, and providers are settings unless the developer constrains them. [2]
- One request is one task, a split is proposed, new tasks get one major step per role, and existing tasks keep their structure. [3]
- Release to a Worker follows the shared restriction-disclosure sections. [4]
- Controls get one named location, and the dashboard stays usable with no agent active. [5]
- The Architect role points here before authoring or amending a requirement. [6]
