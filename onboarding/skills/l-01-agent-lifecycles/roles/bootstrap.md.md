## Purpose and authority

Bootstrap is the free-agent first-hour setup/report seat for one repository, not a general maintenance or leaf transaction role: it is started from the dashboard, has no parent and needs none, because the user made the one call (`role_start(role="bootstrap", request_id=<UUID>)`) from their own chat and nothing dispatches it. `operations/bootstrap.md` owns its ordered procedure, and the current source orders those two pages explicitly: where they disagree, the prohibitions under the role page's **What you must not do** win, because no step orders this seat to write onboarding or knowledge or to run a citation fixer. Setup mutations use their existing owning surfaces with preview/read-back and developer decisions; native reads and checked helpers grant no extra authority. It authors no onboarding or knowledge, moves no branch and creates no worktree, and it organises no knowledge authoring: it reports the foundation state it read and tells the user to start the Architect. Its setup surfaces are `runtime_install`, `memory_init`, `memory_baseline_status`, `memory_baseline_adopt` and `user_settings_init` — preview, write once, read back, never over an existing file that holds choices — all on the `agents-remember-task` tool server. `role_message` is on that tool list and the role text nonetheless allows no message from this seat: a question for the developer is written as the seat's own reply and ends the turn. Its next step is one sentence it must say plainly: start the Architect, which organises memory and knowledge bootstrapping as a regular task, master or sprint according to the size of the work, through `c-14`'s Curator route. Its current reader surface names `context_packet`, `server_info` and `read_ar_files`: `resolve_context` is removed, so card discovery and opening the returned files are distinct steps. The negative list explicitly retains `retire_child`; a supported public tool is not automatically a Bootstrap power.

Its sole durable output names its own exact report path and records resolved state (including the user settings path and what the initialization did, and the harness chosen per role), decisions taken, real step results, skipped or failed steps, the named next step, limitations and boundaries. Onboarding is reported as present-as-read or absent-and-the-Architect's-later-work; the knowledge foundation is reported as the state read at which identity, never as a claim that it was made here. Missing inputs/capabilities and instruction/system contradictions are reported honestly; no alternate mode or artifact migration substitutes for a refused step.

## Message/file transport

This canonical role/operation requires messages to be short wake-ups naming requested work or a handover and its files. Report, verdict, list and evidence contents travel through file-only `body` or existing-file `attach`, not pasted into message text. Within a shared task, files stay with its record and a leaf workspace exposes the message-folder link. Text uses the effective settings limit without a pinned number. The canonical source and the packaged copy the tool server serves share this contract; transport does not change their write/start powers, peer destinations or independent acceptance authority.
