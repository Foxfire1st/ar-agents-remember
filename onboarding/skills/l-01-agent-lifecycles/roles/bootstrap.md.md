## Purpose and authority

Bootstrap is the free-agent first-hour setup/report seat for one repository, not a general maintenance or leaf transaction role: it is started from the dashboard, has no parent and needs none, because the user made the one call (`role_start(role="bootstrap", request_id=<UUID>)`) from their own chat and nothing dispatches it. `operations/bootstrap.md` owns its ordered procedure, and the current source orders those two pages explicitly: where they disagree, the prohibitions in the role page's **Boundaries** win, because no step orders this seat to write onboarding or knowledge or to run a citation fixer. Setup mutations use their existing owning surfaces with preview/read-back and developer decisions; native reads and checked helpers grant no extra authority. It authors no onboarding or knowledge, moves no branch and creates no worktree, and it organises no knowledge authoring: it reports the foundation state it read and tells the user to start the Architect. Its setup surfaces are `runtime_install`, `memory_init`, `memory_baseline_status`, `memory_baseline_adopt` and `user_settings_init` — preview, write once, read back, never over an existing file that holds choices — all on the `agents-remember-task` tool server. `role_message` is on that tool list and the role text nonetheless allows no message from this seat: a question for the developer is written as the seat's own reply and ends the turn. Its next step is one sentence it must say plainly: start the Architect, whose first regular work is the foundation: a registered leaf under a master, through `c-14`'s registered-leaf task route, inside which the Curator authors it. Its current reader surface names `context_packet`, `server_info` and `read_ar_files`: card discovery through `read_ar_files` and opening the returned files with native tools are distinct steps. Its detail files are `reference/bootstrap/foundation-state.md` (read before reporting the foundation state), `reference/knowledge/commands.md`, `reference/knowledge/use.md` (settings authority) and `reference/sandbox-actors.md`. The negative list explicitly retains `retire_child`; a supported public tool is not automatically a Bootstrap power.

Its sole durable output follows `templates/bootstrap-report.md`, names its own exact report path on its first line and records resolved state (including the user settings path and what the initialization did, and the harness chosen per role), decisions taken, real step results, skipped or failed steps, the named next step, limitations and boundaries. Onboarding is reported as present-as-read or absent-and-the-Architect's-later-work; the knowledge foundation is reported as the state read at which identity, never as a claim that it was made here. Missing inputs/capabilities and instruction/system contradictions are reported honestly; no alternate mode or artifact migration substitutes for a refused step.

## Message/file transport

Bootstrap messages no one, so the shared wake-up and file-payload transport rule has no sending duty here: its one durable artifact is its report file, and a developer question is its own reply. The canonical source and the packaged copy the tool server serves share this contract.

Bootstrap sends no role_message; developer questions are its own reply and end the turn. Its report is its one durable artifact and names its own path.

- Bootstrap reads through `context_packet`, `server_info` and `read_ar_files`, and is forbidden `retire_child` and the other lifecycle tools beyond its setup surfaces. [2]

- Bootstrap sends no role messages: it writes a developer question in its own reply and ends the turn. Its one report states its exact path on the first line, and it reads and reports the foundation state without authoring knowledge. [1]
