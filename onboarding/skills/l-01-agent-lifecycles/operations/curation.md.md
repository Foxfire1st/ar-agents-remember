## Memory review and ownership

MEMORY review stays separately sealed/counted and never opens or resets CODE review. Beyond the settings limit the architect or developer authorizes the pass and Manager records it. Curator owns corrected input/body/coherence work; transaction steps and external effects stay with their owners. The installed-build quality/coherence outcome and direct Reviewer handover remain separate from independent acceptance.

## Message/file transport

This canonical role/operation requires messages to be short wake-ups naming requested work or a handover and its files. Report, verdict, list and evidence contents travel through file-only `body` or existing-file `attach`, not pasted into message text. Within a shared task, files stay with its record and a leaf workspace exposes the message-folder link. Text uses the effective settings limit without a pinned number. The canonical source and generated copies share this contract; transport does not change their existing write/start powers, peer destinations or independent acceptance authority.

## Purpose

The curation operation instruction: Curators use it to reconcile a leaf's intent, code and memory and to prepare its memory handover; Managers use it to assign that work and keep transaction and acceptance authority.

## Foundation carrier and writer admission

Repository foundation is regular task work inside the registered leaf the user-started Architect opens under a master, with that leaf's admission and scope. This seat is started on that task document and runs `c-14-knowledge-bootstrap` with its actual enclosure contract; an incidental code delta is not required. Bootstrap reads and reports the foundation state and names the Architect as the next step, and no instructed session substitutes for task admission. The writer keeps its developer commit word and stays the contract-scoped leaf writer. No invented task document or enclosure bridges those admissions.

## Code Commentary

The family rules live in `reference/curator/family-obligations.md`, which the Curator role reads before deciding family coverage or updating a family: restating a guarantee needs a `changed` family history row with the Curator's effect, the writer fills the family revision, families are read back with `knowledge_read` `view="family"`, and every unattributed location the prepared context names is attributed or explained.

Converted-memory closeout additionally requires a non-author second reader. That seat checks every changed card, sidecar and record statement against final code, every history disposition/effect/reason against the diff, and important omissions. Blocking findings are repaired, with a full curation-operation rerun after each repair. This is a lifecycle duty, explicitly not an automated closeout predicate or a Curator-helper self-check.

- Raw clean curation and the independent second-reader fact-check have separate obligations. The intake sentence names the task-read arguments by their dotted path, `documents[0].taskDocReadArgs`, which is where a first message's projection carries them. [2]

## Current composition and authoring contract

Curation remains the leaf coherence pass and the bounded repository-foundation authoring procedure. Common text retains the captured candidate range, packet rejection, disjoint Curator/Manager transaction ownership, serving-build-only producer, full quality loop, independent non-author fact-check and protected closeout/sync/permission boundaries. Curator-only method details do not enter Manager's stage slice.

The complete Curator intake and result live in roles/curator.md. Its named-step references carry the detailed reconciliation, record and family authoring, card and citation formats, commands and read signatures, in the topic files under `reference/curator/` and `reference/knowledge/`; family effect and revision rules are in `reference/curator/family-obligations.md`.

Current curation continues from a report to the next authorized step without a new Manager go. It verifies card sentences against source, repairs wrong or missing memory encountered along its way beyond quality-check findings, names each repair and makes no broad sweep. Code changes, requirement decisions and another leaf’s work return to their owner. A correction qualifies every affected false body claim; full checks and the independent fact-check run before handover.

Reviewer records memory begin/result with `reviewKind=memory`, retaining separate sealed IDs, reports and count under the code-review limit, without opening/resetting a code round. Architect/developer approval for extra passes is recorded by Manager. Direct handovers, pending Manager-notice recovery and one admitted Curator writer remain.

Before writing memory, the Curator reads `worktree_status` for the assigned task and inspects its source-freshness observation; this read is informational and grants no sync or approval authority and adds no cleanliness or known-staleness gate. Staleness known at task intake is the task's curation work: stale assigned or encountered memory, including pre-existing staleness, is repaired without a whole-memory sweep. A multi-repository check covers every enabled repository first and presents the results together before asking about updates. If one memory tool fails, independent work continues through the other admitted memory tools, while existing refusal stops still bind dependent work.
