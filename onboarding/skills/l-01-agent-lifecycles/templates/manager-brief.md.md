## Current Canonical Contract

The template supplies master-document values, not a separate rule authority. A Manager starts with role_start and the master reference, naming its sprint when a sprint commands that master; the call carries no pasted brief. Source-edge selection follows execution nature and supported sync, not a guessed checkout branch. Leaf seats start individually through role_start: Worker at build, Reviewer at freeze and Curator after code PASS. One owned primary revision is compiled separately from dependency/preservation requirements, and formal handoff attempts remain distinct from internal experimental reruns. Requested review keeps a sealed, monotonic finding set with settings-bound extra-round authority; the Reviewer records CODE while the Manager retains transaction decisions. Closeout-door and queue facts do not lock valid task edits or create permission to land. The source explicitly keeps complete curator memory quality as a standing operation whose result the Git transaction carries, not an opt-in full-test rule.

Host archival retains reports at leaf finalization/cleanup/abandonment, excludes Manager/Orchestrator, and `retire_child` and seat replacement follow role scope in `core/every-role.md` (Manager covers its master and leaves).

## Sealed review and transaction ordering

The compiled master brief preserves the monotonic sealed finding list across rounds within the settings limit and names recorded architect/developer approval beyond it. Values in the brief cannot create a routine transaction gate or alter role/operation authority; direct peer file packages and Manager transaction ordering remain separate.

## Closeout

The brief publishes no closeout door. After the handoff and a current-lineage proof, the leaf is closed out through its own procedure — `worktree_closeout_preview`, then the approval stop (the Manager's standing leaf authority for routine leaves, which answers the clean preview's approval question, or the developer's commit approval for final work), then `worktree_closeout_apply` with an explicit nonblank message per enabled leg and that authority as its intent note. Before apply, the Manager confirms the required curation evidence, including the Curator’s coherence validation when the checklist requires it. Apply checks task intent, super → master → leaf lineage and the knowledge gate, then records transaction evidence per leg. No release by an Orchestrator is needed. Before retrying, read the apply result and any per-leg transaction evidence. Correct the blocker and rerun the same tool with the applicable authority and explicit messages for enabled legs. Re-prove affected evidence after a task edit. `closeout_queue` is only the sprint's disposable waiting-only projection (`status`, `rebuild`) and confers no authority.

## Message/file transport

This canonical template requires messages to be short wake-ups naming requested work or a handover and its files. Report, verdict, list and evidence contents travel through file-only `body` or existing-file `attach`, not pasted into message text. Within a shared task, files stay with its record and a leaf workspace exposes the message-folder link. Text uses the effective settings limit without a pinned number. The canonical source and the packaged copy share this contract; transport does not change their existing write/start powers, peer destinations or independent acceptance authority.

## Purpose

This is the template the Orchestrator or Architect uses to prepare a Manager's master documents and
start inputs for one master; the `role_start` call carries no brief, and the Manager's first message is compiled from the documents. It transfers task topology, source-edge truth, targeted/scoped evidence, closeout scheduling, and
the exact approved requirement revisions the manager must dispatch and close.

## Code Commentary

### Logic

Before Worker dispatch, the Manager receives the primary revision's stable ID, exact version, approved canonical packet, durable approval record and expected evidence classes, with dependency and preservation context listed separately.
The Manager requires one Worker acceptance block and an independent adjudication for the owned primary revision. It separately preserves the durable-evidence promotion hold point, optional requested
review, curator handoff, and repository-defined transaction boundaries.

The brief also requires the manager to compile the next review-handoff attempt identity without
advancing it during dispatch or internal implementation/test/evidence reruns, validate the
lightweight candidate-bound worker record and content-addressed expanded-evidence anchor, and
dispatch that exact candidate to independent review. The rebuildable master summary links authoritative
leaf journals, excludes separate protocol events from attempt counts, and never gates task,
lifecycle, closeout, integration, or queue work.

A reviewer-rejected manifestation creates a successor at the next handoff; an unrelated later
candidate does not reopen accepted work.

The brief also keeps task authoring independent of disposable closeout projections: valid task
mutations proceed, projection effects are reported,
and queue state is never treated as a task lock.

### Conventions

- The preparer (Orchestrator or Architect) fills every placeholder before the start.
- Canonical task documents and contracts owned by the lifecycle tools carry branch and source identity.
- Stable requirement IDs and versions are copied exactly; master prose never replaces packets.
- Worker, reviewer, and curator seats remain distinct; the reviewer is also distinct from the seat
  that authored the plan, preventing plan-author self-adjudication.

### Invariants And Boundaries

- An unstable, unapproved, missing, duplicated, or version-mismatched requirement makes dispatch
  invalid.
- Any rejected requirement blocks the overall reviewer recommendation.
- Requirement acceptance cannot substitute for stable-contract-or-expiry evidence, or vice versa.
- A manager reports readiness but does not rank the portfolio or decide developer-owned gates.
- Requirement problems route to architect/developer revision authority; worker/reviewer records
  cannot change semantic versions.
