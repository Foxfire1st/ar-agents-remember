## Purpose

Selective converted paired-card/record reconciliation into an exact open recovery leaf after code lands; not a merge or a content-commit producer.

## Code Commentary

Plan is read-only and files no report. Equal converted-format roots are required before later reads. Source/official refs and old base establish every-touching-commit ancestry, patch identity or final-content proof; overlap alone requires review and unlanded code rejects. Markdown and sidecar are one unit; routes, memory-only documents and the entity catalog retain distinct selection keys and review boundaries.

Anchors are observed at official code. Current or unchanged moved anchors can be re-recorded; stale/unresolved/unreadable anchors need explicit review, never a fabricated current result. Missing transitive records may be carried, but differing held records and unrelated edited targets are not overwritten. Source history is reading aid only, never imported answers.

Apply validates the exact uncommitted resulting tree against the recovery base and official code and restores its owned extent on refusal. It commits nothing and refreshes no ledger cache; retries skip already-equal writes and report conflicting edits. Recovery curator own source-bound rows and ordinary gated closeout/integration own publication. No protected-ref fallback or permission for a manual sidecar/anchor exists.

> ## Purpose

> This skill describes selective carryover of richer source-branch onboarding after corresponding code has landed on a protected official branch, including delayed or batched merges from personal, feature or handpicked reconciliation branches. It documents candidate proof and an external recovery-leaf boundary, not a normal Git merge or a converted-memory apply permission.

> ## Code Commentary
>
> ### Selection and branch roles
>
> The reconciliation model distinguishes official code, source-branch code, official memory, source-branch memory and the old base. It proves which source changes are represented at the selected official ref before carrying corresponding onboarding. Planning precedes report review and explicit apply intent; the source names the MCP/package route rather than executable skill-tree logic. The target is a dedicated open external-memory recovery leaf created from the landed pair, whose separate ordinary closeout and integration own publication. These are descriptions of the legacy-format carryover contract; the format guard described below still determines whether apply is admitted.
>
> For code-diff candidates, proof tiers descend through `exact-landed-commit`, `patch-id-match`, `final-content-match`, `same-path-changed` and `not-landed`. Exact-landed means every source-branch commit touching the path landed, not merely one earlier commit. Patch identity or final content equality can also establish equivalence. Same-path overlap alone is review-required, because another developer may have changed the file independently; unlanded code is not carried.
>
> ### Historical ledger and protected-ref behavior
>
> The inherited GitHub #54 account described `ledger-mapped-head`: an unmapped official code HEAD such as a PR merge commit was mapped to the current memory content commit. It also described an apply result’s `memory_main_advance` with `fast-forwarded`, `already-current`, `diverged`, `failed` and `skipped` states, and a developer-approved push of memory `main` through repository Git policy. These are historical output meanings, not current apply results or permission to move protected refs.
>
> The present source instead describes an ignored `memory.md` cache regenerated from target memory commit trailers, never staged or committed and never copied from source cache rows. Missing/malformed cache data does not block carryover. Unchanged content retains the actual memory commit; a new code SHA does not create a synthetic mapping-only commit, and regeneration does not rewrite historical attribution. Carryover never writes or force-moves memory `main`, sprint-super or atomic integration refs. Protected-ref movement belongs to the recovery leaf’s separate journaled integration.
>
> ### Candidate kinds and validation
>
> The four candidate kinds retain distinct review selection keys: `file-sidecar` uses its source path; `route-overview` uses the normalized route, with `.` for root; `memory-only-doc` uses its source path or route; `entity-catalog` uses the literal `entity-catalog`. Memory-only documents cover branch-memory-only changes outside the code diff. A differing entity catalog is whole-file and review-required, not entry-merged; `git-blob-set-v1` fingerprints are recomputed against the official code ref, with `entity_fingerprint_validation` states `validated`, `mismatch` or `skipped` and per-entity detail rather than trust in copied derived values. The inherited versioned coverage account also emphasized that every path-touching source commit must have landed.
>
> Memory-only candidates auto-carry only under `memory-only-reverification-valid`: the object at the branch document’s verification commit matches the official ref and target recovery memory has not independently changed that document since its memory merge-base. `source-diverged`, `target-memory-moved` and `unverifiable` require review; absent official objects are not landed. Unresolvable verification commits or merge bases do not establish validity. These metadata-dependent rules describe the retained legacy candidate model, not converted-card metadata.
>
> ### Review, replacement and output model
>
> The skill’s output is state-oriented and JSON-friendly. Planning reports `would-carryover`; the legacy apply body describes `carried-over`, `nothing-to-carryover` and `blocked`. `carried-over` means a recovery-leaf memory-content commit attributed by `Code-Commit` to the selected official code commit, not protected-ref publication. `blocked` covers absent approval/intent, an open recovery contract, a clean exact landed base or required candidate data. Existing different target onboarding is not overwritten without opt-in `replace_existing=true` or explicit `include_review_required` selection; the inherited CLI spelling was `--replace-existing`. These states describe the retained contract and code body, not an observed successful apply.
>
> ### Converted-memory and authority boundaries
>
> The inherited invariants prohibit copying memory for unlanded code, copying source ledger rows wholesale, or refreshing verification against the source branch rather than official code. The current source derives the target cache from target history and reserves `c-02-memory-quality-control` as branch-accuracy drift detection; carryover only selects proven or explicitly reviewed richer onboarding. Metadata refresh belongs to its legacy format.
>
> The actual apply owner validates runtime configuration and repository identity, exact external leaf/worktree binding, open closeout/integration state, ordinary-worktree status and a clean code worktree whose base and HEAD equal the selected official tip. Crucially, `_require_legacy_format_target` runs before the copy/metadata/commit body. A converted target raises the named `CONVERTED_TARGET` refusal and directs curation to the file writer. Unconverted targets are subjected to the central cutover lock; that guard is not a legacy-write exemption. The canonical converted-card workflow explicitly lists `memory_carryover_apply` among forbidden converted-memory actions. A candidate plan therefore does not authorize importing legacy Markdown or manually carrying companion reference/typed tuples into converted memory.
