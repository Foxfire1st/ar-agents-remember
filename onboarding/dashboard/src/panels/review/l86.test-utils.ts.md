# dashboard/src/panels/review/l86.test-utils.ts

## Governing Overview

[Review route overview](overview.md)

## Purpose

Serve the shared L86 mounted-test world from the retained L37 public captures, with request logging and optional held lane/worklist replies. The added summary response is explicitly composed, not another raw captured answer.

## Code Commentary

`captured` parses the retained fixture file. Member identity comes from the recorded invariant-selector request in capture provenance and must match the member body's selected record, or loading fails. The target names the recorded L37 leaf. `serve` logs requested URLs and can hold a lane or unscoped worklist response until released.

`intentReply` chooses member, family or task replies by selector. `treeReply` distinguishes file classification, lane, leaf-wide inventory and member/family card sets by query. `replyFor` keeps these routes, the source-content fixture and changeset/diff fixtures; an uncaptured route throws.

The new `/api/review/intent/summary` branch returns the module's composed `summary`: attribution totals are copied from the captured lane; intent counters are literal zero values, and the unmeasured list is empty. These supplied test-world values are neither a newly captured production summary nor proof that this leaf or its captured L37 subject has zero changed intent. The fixture files retain their bytes; the new response is identified separately rather than passed off as captured evidence.

## Invariants And Boundaries

This support source declares no tests and proves no product summary-count contract by itself. The stored fixtures and composed summary have distinct provenance. Optional response holding is test control, not production latency behavior.

## Evidence

- The loader parses each named retained capture. [1]
- The selected invariant is read from exact request provenance and checked against the captured member body. [2]
- The shared mounted target names the recorded L37 leaf. [3]
- The fetch stub logs requests and can hold selected lane or worklist responses. Held-response selection distinguishes lane from unscoped worklist requests. [4]
- The reply router dispatches the exact supported public paths and throws for any other route. Intent and tree replies are selected by their selector and tree query parameters. [5]
- The summary response is composed from captured lane attribution counts with literal zero intent counters; it was not captured with L37. [6]
